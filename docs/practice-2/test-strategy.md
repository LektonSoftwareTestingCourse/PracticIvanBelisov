# Тестовая стратегия СМП

## 1. Цель тестирования
Проверить, что процессинговая цепочка проходит целиком от терминала до дашборда. Система должна гарантировать точность списания средств и отдавать корректные статус-коды отказов для любых сценариев

## 2. Объект тестирования
СМП целиком:
- Ядро: Authorization Service, Card Management Service
- Периферия: Gateway, Switch, Bin Lookup, Terminal Simulator, Logger, Dashboard
- Инфраструктура: PostgreSQL, RabbitMQ

## 3. Уровни тестирования
- **Модульное**: чистая логика без сети (алгоритм Луна, формат даты, генерация RRN)
- **Компонентное (API)**: контракты сервисов ядра в изоляции (проверка каскада авторизации)
- **Интеграционное**: межсервисные стыки (Switch -> Bin Lookup, Auth -> CMS)
- **Сквозное (E2E)**: полный путь транзакции в собранном Docker-контуре

## 4. Область тестирования
**Что войдет:**
- Проверки авторизации
- CRUD карт, алгоритм Луна, мягкое удаление (`status = DELETED`)
- Резервирование средств и отработка таймаутов

**Что не войдет и почему:**
- **Нагрузочное тестирование**: требует отдельного стенда, также операции проверки и списания не атомарны, соответственно гонка данных под нагрузкой ожидаема
- **Безопасность**: работа только с тестовыми данными (данные карт заменены заглушками)
- **UI-тесты**: графический интерфейс не является приоритетом для процессинга

## 5. Риск-ориентированный подход
Ядро системы несет прямые финансовые риски, поэтому оно тестируется плотно: классы эквивалентности, границы и попарное тестирование. Периферия несет меньше рисков, поэтому ее покрываем только чек-листами дымового тестирования и критического пути.

Принципы приоритизации:
1. Наивысший приоритет отдается сценариям способным принести прямые убытки системе: обработка превышения лимитов, нехватки средств на балансе и защита от повторного резервирования
2. Валидация бизнес-поведения системы (проверки, обновление счетчиков) имеет приоритет над проверками отображения транзакций и интерфейса
