# Тестовый план СМП

## 1. Область и подход

### Область тестирования:
- Ядро (Authorization Service, Card Management Service): функциональное тестирование бизнес-правил, каскада проверок, лимитов, балансов и CRUD карт.
- Периферия (Gateway, Switch, Bin Lookup, Logger, Dashboard): интеграционные проверки доступности, маршрутизации и сквозных цепочек.

### Применяемые техники тест-дизайна:
- Классы эквивалентности: для валидации входных данных API и статусов карт
- Граничные значения: трехточечный анализ (ON, OFF-ниже, OFF-выше) для лимитов, остатка баланса и срока действия карт
- Попарное тестирование: комбинаторное сжатие параметров авторизации с помощью утилиты pict

### Инструменты и стек автоматизации:
- Среда исполнения: Docker Compose и Testcontainers для интеграционных прогонов
- Стек автотестов: Java 21, фреймворк JUnit 5, библиотека REST Assured (HTTP-запросы и валидация ответов API)
- Генерация комбинаторных данных: утилита `pict`
- Базы данных и очереди: прямое обращение к PostgreSQL через JDBC (для контроля таблиц `limit_usage` и `outbox_event`)

### Метрики покрытия и качества:
- Покрытие требований ТЗ: 100% бизнес-правил из ТЗ 04 и 05 покрыто тестами или чек-листами
- Покрытие пар: 100% допустимых пар параметров из pict
- Процент успешных тестов: не менее 95%
- Критичность дефектов: 0 открытых багов уровня Blocker и Critical на момент релиза

## 2. Критерии входа и выхода

### Критерии входа:
- Сервисы СМП собраны без ошибок компиляции, Docker-контейнеры запущены в одной сети
- Эндпоинты `GET /health` всех сервисов возвращают HTTP 200 OK
- База данных PostgreSQL инициализирована, миграции таблиц `cards`, `limit_usage`, `outbox_event` применены
- Сгенерирован начальный пул карт
- Модель `model.txt` и набор `cases.txt` согласованы

### Критерии выхода:
- Все запланированные тест-кейсы ядра и пункты чек-листов периферии выполнены
- Нет открытых дефектов категорий Blocker и Critical
- На все decline-сценарии система стабильно отдает верные коды
- Достигнут целевой Pass Rate >= 95%

### Критерии приостановки и возобновления:
- **Приостановка**: падение PostgreSQL, неработоспособность эндпоинта `POST /api/cards/generate` или блокирующий сбой в Switch, при котором запросы не доходят до авторизации
- **Возобновление**: устранение блокирующего дефекта, обновление Docker-образа, успешный прогон smoke-чеков и откат БД к эталонному состоянию

## 3. Ресурсы и расписание

### Роли и ресурсы:
- QA инженер: проектирование тест-кейсов, генерация pairwise-набора в pict, выполнение проверок, заведение дефектов
- Backend разработчик: исправление багов в коде авторизации, логике Луна и резервирования
- Окружение: локальная станция с Docker Desktop, Git и терминалом

### Расписание:
- Дни 1-10: Написание тест-кейсов и подготовка моков
- Дни 11-13: Интеграционное тестирование
- День 17: E2E-прогоны и нагрузка

## 4. Риски
1. **Неатомарность чтения и резервирования баланса**
    - *Риск*: гонка состояний между получением карты и вызовом `/reserve`
    - *Решение*: выполнять функциональные тесты по одной карте строго последовательно
2. **Флакающие проверки таймаутов Bin Lookup**
    - *Риск*: нестабильные задержки реальной сети при проверке фоллбэка
    - *Решение*: использовать локальный стаб с предсказуемой задержкой 
3. **Загрязнение счетчиков лимитов в `limit_usage`**
    - *Риск*: накопленные суммы прошлых транзакций искажают проверки граничных значений
    - *Решение*: изолировать тесты по уникальным номерам карт либо сбрасывать таблицу перед проверкой границ
